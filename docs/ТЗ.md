## 1. Контекст

**Заказчик.** АО «Москоллектор» эксплуатирует инженерные коллекторы Москвы (§2):

| Объект | Объём |
|---|---|
| Коллекторы | 825 км |
| Кабели связи | 19,7 тыс. км |
| Силовые кабели | 8,3 тыс. км |
| Тепловые и водопроводные сети | 1,9 тыс. км |

**Проблемы сейчас** (§2):

- реактивная работа — реагируют только после срабатывания датчиков;
- ложные тревоги — значительная доля всех срабатываний;
- ТО проводится по фиксированным срокам, без учёта реального состояния оборудования.

**Цель** (§3, §4): сервис предиктивной аналитики, который прогнозирует инциденты и поддерживает принятие решений при планировании ремонтов.

**Пользователи** (§3):

- диспетчеры ОДС и эксплуатационных подразделений — основной пользователь;
- технический персонал по обслуживанию коллекторов;
- руководители эксплуатационных подразделений;
- аналитик — отвечает за верификацию данных (появляется в сценариях, §12).

**Стратегическое соответствие** (§2): Стратегия развития строительной отрасли и ЖКХ РФ до 2030 г., Национальная стратегия развития ИИ, федеральный проект ИИ нацпроекта «Экономика данных».

## 2. Обязательные задачи

### 2.1. Ключевые задачи сервиса (§4)

- [ ] Прогнозирование отказов датчиков и инженерных систем до их фактического возникновения.
- [ ] Раннее выявление рисков пожаров и подтоплений.
- [ ] Аналитическая поддержка при верификации фактов несанкционированного доступа.
- [ ] Рекомендации по техническому обслуживанию на основе данных о состоянии оборудования.
- [ ] Выявление ложных срабатываний — снижение числа ложных выездов (§2).

### 2.2. Прогнозирование инцидентов (§6)

- [ ] Анализ данных с датчиков для выявления рисков.
- [ ] Расчёт **вероятности** инцидента с **горизонтом не менее 24 часов**.
- [ ] Определение **локации** оборудования, подверженного риску.
- [ ] **Классификация типа** прогнозируемого инцидента.

### 2.3. Сценарный анализ (§6)

- [ ] Анализ сценариев инцидентов на исторических данных: **пожар, проникновение, подтопление**.
- [ ] Превентивные уведомления на основе прогнозных моделей.
- [ ] Рекомендации по ТО и ремонту на основе анализа состояния оборудования.

### 2.4. Границы решения — что сервис должен (§5)

- [ ] Анализировать исторические и текущие данные мониторинга.
- [ ] Обрабатывать журналы диспетчерской службы.
- [ ] Работать с реестрами оборудования.
- [ ] Выдавать прогнозы с указанием вероятности и временного горизонта.
- [ ] Выполнять предиктивное моделирование инцидентов на исторических данных.
- [ ] Интегрироваться с существующими системами мониторинга для получения данных.

Сервис обязан обеспечивать:

- [ ] точность прогнозов не ниже установленных показателей;
- [ ] своевременное информирование о потенциальных угрозах;
- [ ] удобный интерфейс для диспетчеров;
- [ ] надёжную интеграцию с существующими системами;
- [ ] защиту данных от несанкционированного доступа.

### 2.5. Работа с данными (§6, §7)

- [ ] Сбор данных из системы мониторинга **СМВУ**.
- [ ] Обработка журналов **ОДС**.
- [ ] Анализ реестров инженерного оборудования.
- [ ] Интеграция с системой учёта заявок — получение статусов.

Входные данные:

| Источник | Способ |
|---|---|
| Исторические данные | импорт CSV / XLSX |
| Потоковые данные СМВУ | API / очередь сообщений |
| Журналы ОДС | загрузка через API |
| Реестр оборудования | цифровой формат |

Форматы обмена:

| Канал | Формат |
|---|---|
| Файлы | CSV, XLSX |
| API | JSON, XML |
| СУБД | PostgreSQL (или иная СУБД инфраструктуры заказчика) |
| Геоданные | GeoJSON, WKT |

### 2.6. Пользовательский интерфейс (§10)

- [ ] **Дашборд** — веб-интерфейс для диспетчеров с визуализацией уровней риска.
- [ ] **Интерактивная карта** — объекты инфраструктуры с выделением проблемных зон.
- [ ] **Журнал прогнозов** — реестр событий с историей прогнозов и результатами их отработки.
- [ ] **Уведомления** — оповещение о критических инцидентах в реальном времени.
- [ ] **Фиксация решения диспетчера** с выбором причины из справочника («выезд бригады», «ложное срабатывание», «мониторинг ситуации» и т. п.) — сохраняется в журнал для анализа и дообучения (§12).

UX/UI (§16):

- [ ] Интерфейс доступный и удобный, путь пользователя интуитивно понятен.
- [ ] Каждый элемент решает конкретную задачу и присутствует на экране, только если он нужен.
- [ ] Логически связанные блоки размещены рядом (§18).

### 2.7. Интеграция (§10)

- [ ] **REST API** для получения данных из внешних систем.
- [ ] Получение данных о состоянии оборудования из систем мониторинга — **только чтение**.
- [ ] Автоматическая синхронизация реестров оборудования из учётных систем заказчика.

### 2.8. Производительность и качество (§9, §11)

| Требование | Значение |
|---|---|
| Inference для одного объекта | ≤ 300 с (5 мин) |
| Задержка обработки потока | ≤ 300 с (near real-time) |
| Одновременные пользователи | ≥ 20 без деградации |
| Горизонт прогноза | ≥ 24 ч |
| Precision / Recall | определяются на этапе проектирования по качеству данных |

### 2.9. Надёжность (§11)

- [ ] Автоматическое резервное копирование данных.
- [ ] Восстановление после сбоя — не более 4 часов.

### 2.10. Безопасность (§11, §13, §14)

- [ ] Шифрование при передаче — TLS 1.2+.
- [ ] Аутентификация через корпоративный каталог — LDAP / AD.
- [ ] Ролевая модель доступа — RBAC.
- [ ] Журналирование всех действий пользователей.
- [ ] Интеграция с системами заказчика — только Read-only.
- [ ] Соответствие 149-ФЗ «Об информации…» и 152-ФЗ «О персональных данных».

### 2.11. Инфраструктура (§11)

- [ ] Серверная часть — Linux.
- [ ] Браузеры — актуальные Google Chrome и Яндекс.Браузер.
- [ ] СУБД — PostgreSQL 12+.
- [ ] Хранение разделено на оперативный контур, архив и аналитические витрины (§13).

### 2.12. Требования к решению и коду (§14)

- [ ] Отдельный сервис, который может стать самостоятельной ИС или её компонентом.
- [ ] Количество внешних интеграций соответствует целям и задачам.
- [ ] Все методы доступны и подробно описаны.
- [ ] Перечень всех использованных библиотек и компонентов.
- [ ] Комментарии к сложным техническим и логическим местам.
- [ ] Открытый, неоткомпилированный исходный код без обфускации.

### 2.13. Сопроводительная документация (§14)

- [ ] Используемые методы обработки данных.
- [ ] Условия и ограничения решения.
- [ ] Подробные инструкции по компиляции, сборке и установке.
- [ ] Функциональная и компонентная архитектура.

### 2.14. Презентация (§15)

- [ ] Формат pptx или pdf.

## 3. Побочные задачи

Не функции сервиса из §6–§11, но прямо проверяются на экспертизе (§17, §18) или нужны, чтобы проверка была возможна.

- [ ] **Проверка прогнозов на реальных данных** — сравнение прогнозных значений с фактическими, оценка достоверности (бэктест, метрики).
- [ ] **Проверка рекомендаций** — сравнение рекомендаций сервиса с реальными рекомендациями при тех же вводных.
- [ ] **Проверка расчётов** — корректность вычислений.
- [ ] **Дополнительные настраиваемые параметры** — пороги, горизонт, чувствительность и т. п.
- [ ] **Объективность диаграмм** — графики должны читаться и честно отражать данные.
- [ ] **Скорость и удобство работы** интерфейса.
- [ ] **Возможность интеграции в любые другие системы**.
- [ ] **Работающий прототип** по ссылке — для проверки жюри.
- [ ] **Питч-сессия** — выступление команды.

## 4. По согласованию с заказчиком

Реализуются «по согласованию с Заказчиком в рамках развития функционала сервиса» (§8) — не обязательны, но дают плюс.

Расширенная аналитика:

- [ ] Детальная статистика по типам инцидентов.
- [ ] Исторические отчёты по ремонтам.
- [ ] Прогнозная аналитика с учётом сезонных изменений.

Дополнительные модули:

- [ ] Модуль дообучения прогнозных моделей на новых данных.
- [ ] Система рекомендаций по профилактическому обслуживанию.
- [ ] Черновики заявок на ремонт на основе рекомендаций системы.

Дополнительные интерфейсы:

- [ ] Аналитические отчёты для руководства в PDF и XLSX.

Параметры, которые ТЗ оставляет на заказчика или проектирование:

- целевые Precision и Recall — по качеству данных (§9);
- доступность системы — по регламенту эксплуатации ИС заказчика (§11);
- СУБД — PostgreSQL или иная из инфраструктуры заказчика (§7);
- обфускация (обезличивание) данных — выполняется на стороне источника (§7).

## 5. Что сервис НЕ должен делать

Прямо запрещено (§5):

- ❌ Замещать работу диспетчеров.
- ❌ Принимать окончательные решения об инцидентах — решение всегда за диспетчером.
- ❌ Управлять инженерным оборудованием напрямую.
- ❌ Проводить ремонтные работы.

Следует из других разделов:

- ❌ Писать что-либо во внутренние системы заказчика — только чтение (§10, §13).
- ❌ Обфусцировать или отдавать скомпилированный код (§14).
- ❌ Раскрывать персональные данные — данные приходят обезличенными, 152-ФЗ (§7, §14).
- ❌ Выводить элементы интерфейса, которые не решают задачу пользователя (§16).

## 7. Пользовательские сценарии

Участники обоих сценариев: диспетчер (основной пользователь) и аналитик (верификация данных).

### 7.1. Прогноз пожара (§12)

Предпосылки: накоплена история инцидентов; сервис интегрирован с датчиками и реестром плановых работ.

1. **Анализ** — сопоставление текущих показаний (температура, задымление) с плановыми работами и историческими паттернами.
2. **Прогноз** — при аномалии рассчитывается вероятность инцидента и формируется предупреждение.
3. **Уведомление** — на дашборде: вероятность, временной горизонт, локация объекта.
4. **Верификация** — диспетчер анализирует данные, при необходимости смотрит внешние источники (камеры).
5. **Решение** — диспетчер фиксирует решение («выезд бригады» / «ложное срабатывание») с причиной из справочника.
6. **Завершение** — решение сохраняется в журнал для анализа и дообучения модели.

### 7.2. Прогноз подтопления (§12)

Предпосылки: накоплена история подтоплений; сервис интегрирован с датчиками и внешними метеоданными.

1. **Анализ** — частота включения насосных станций сопоставляется с прогнозом метеослужб и историческими паттернами подтоплений.
2. **Прогноз** — при аномалии рассчитывается вероятность и формируется предупреждение.
3. **Уведомление** — на дашборде: вероятность, горизонт, локация.
4. **Верификация** — анализ данных, при необходимости камеры.
5. **Решение** — «направление бригады на проверку» / «мониторинг ситуации» с причиной из справочника.
6. **Завершение** — решение сохраняется в журнал.

Ожидаемый результат: своевременное информирование о рисках, фиксация мер в системе, накопление данных для повышения точности.

## 10. Неясности и противоречия в ТЗ

- **Число пользователей:** §9 — «все пользователи без деградации», §11 — «не менее 20». Ориентир — 20.
- **Время прогноза:** §9 — 5 минут, §11 — 300 секунд. Это одно и то же.
- **Точность:** §5 требует «не ниже установленных показателей», но §9 говорит, что показатели определяются на этапе проектирования. Цифры нужно задать и обосновать самим.
- **Реальные данные** не приложены — только пример схемы. До их выдачи нужны синтетические данные по этой схеме.
- **Заявки на работы** — нужна интеграция «получение статусов» (§6), а черновики заявок — только по согласованию (§8).
- **Роль аналитика** есть в сценариях (§12), но отсутствует в списке пользователей (§3).
- **Критический инцидент** в терминах — «событие, угрожающее жизни человека»; именно о таких нужны уведомления в реальном времени (§10).
