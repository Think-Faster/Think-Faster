## 1. Контекст и назначение

### 1.1. Компания и проблема (§2)

АО «Москоллектор» отвечает за эксплуатацию и обслуживание инженерных коллекторов Москвы:

| Объект | Объём |
|---|---|
| Коллекторы | 825 км |
| Кабели связи | 19,7 тыс. км |
| Силовые кабели | 8,3 тыс. км |
| Тепловые и водопроводные сети (теплотрассы) | 1,9 тыс. км |

Сейчас компания использует систему мониторинга и диспетчерскую службу. Недостатки текущего подхода:

- реактивный характер работы — специалисты реагируют только после срабатывания датчиков;
- ложные тревоги составляют значительную часть всех срабатываний;
- обслуживание оборудования проводится по фиксированным срокам без учёта реального состояния.

Соответствие стратегиям: Стратегия развития строительной отрасли и ЖКХ РФ до 2030 года; Национальная стратегия развития ИИ; Федеральный проект ИИ в рамках национального проекта «Экономика данных».

**Сервис позволит** (§2):

- заранее выявлять потенциальные риски отказов оборудования;
- снижать количество ложных тревожных выездов на объекты за счёт выявления ложных сработок;
- повышать эффективность эксплуатации инфраструктуры;
- оптимизировать затраты на обслуживание;
- повышать безопасность эксплуатации инженерных систем.

**Сервис будет решать задачи** (§2):

- прогнозирование отказов датчиков и инженерных систем до их фактического возникновения;
- раннее выявление рисков возникновения инцидентов;
- повышение безопасности эксплуатации инженерных коллекторов;
- оптимизация процессов технического обслуживания.

### 1.2. Предназначение сервиса (§3)

Повышение эффективности управления эксплуатацией инженерной инфраструктуры АО «Москоллектор» путём внедрения технологий предиктивной аналитики.

Ключевые задачи:

- прогнозирование отказов инженерных систем до их фактического возникновения;
- оптимизация работы диспетчерской службы;
- оптимизация процессов технического обслуживания;
- повышение безопасности эксплуатации инженерных коллекторов.

**Сервис будет использоваться для:**

- мониторинга общего состояния инженерных систем коллекторного хозяйства;
- контроля работы датчиков инженерных систем и систем безопасности;
- поддержки планирования профилактических работ;
- аналитической поддержки при управлении инцидентами.

**Основные пользователи:**

- диспетчеры объединённой диспетчерской службы (ОДС) и эксплуатационных подразделений;
- технический персонал по обслуживанию коллекторов;
- руководители эксплуатационных подразделений.

На основе предиктивного анализа система **формирует прогнозы возможных инцидентов и рекомендует превентивные меры**.

> 💬 **Прим. команды.** В сценариях (§12) дополнительно участвует **аналитик** (ответственный за верификацию данных), в списке пользователей §3 его нет.

## 2. Обязательные задачи

### 2.1. Постановка задачи (§4)

Разработать сервис предиктивной аналитики для прогнозирования инцидентов и поддержки принятия решений при планировании ремонтных работ в инженерных коллекторах Москвы.

Сервис должен обеспечить:

- [ ] автоматизированное выявление потенциальных рисков и угроз;
- [ ] оптимизацию работы диспетчерской службы за счёт предоставления аналитических данных;
- [ ] повышение эффективности технического обслуживания инженерной инфраструктуры.

Задачи, которые сервис должен решать:

- [ ] прогнозирование отказов датчиков и инженерных систем до их фактического возникновения;
- [ ] раннее выявление рисков возникновения пожаров и подтоплений;
- [ ] аналитическая поддержка при верификации фактов несанкционированного доступа;
- [ ] формирование рекомендаций по проведению технического обслуживания на основе данных о состоянии оборудования.

> 💬 **Прим. команды.** Выявление ложных сработок прямо названо в §2 («снижать количество ложных тревожных выездов за счёт выявления ложных сработок») и в описании проблемы. В перечне задач §4 отдельным пунктом его нет, но это заявленная ценность сервиса.

### 2.2. Границы решения — что сервис должен (§5)

- [ ] Анализировать исторические и текущие данные мониторинга.
- [ ] Обрабатывать информацию из журналов диспетчерской службы.
- [ ] Работать с реестрами оборудования.
- [ ] Предоставлять прогнозы инцидентов с указанием вероятности и временного горизонта.
- [ ] Осуществлять предиктивное моделирование инцидентов на основе исторических данных.
- [ ] Интегрироваться с существующими системами мониторинга для получения данных.

Сервис обязан обеспечивать:

- [ ] точность прогнозов не ниже установленных показателей;
- [ ] своевременное информирование о потенциальных угрозах;
- [ ] удобный интерфейс для работы диспетчеров;
- [ ] надёжную интеграцию с существующими системами;
- [ ] защиту данных от несанкционированного доступа.

### 2.3. Общие требования к сервису (§6)

**Прогнозирование инцидентов**

- [ ] Анализ данных с датчиков для выявления потенциальных рисков инцидентов.
- [ ] Расчёт вероятности инцидентов с горизонтом прогнозирования **не менее 24 часов**.
- [ ] Определение локации оборудования, подверженного риску.
- [ ] Классификация типов прогнозируемых инцидентов.

**Сценарный анализ инцидентов**

- [ ] Анализ сценариев инцидентов (пожар, проникновение, подтопление) на основе исторических данных.
- [ ] Формирование превентивных уведомлений об инцидентах на основе прогнозных моделей.
- [ ] Формирование рекомендаций по техническому обслуживанию и ремонту на основе анализа состояния оборудования.

**Работа с данными**

- [ ] Сбор информации из системы мониторинга СМВУ.
- [ ] Обработка журналов диспетчерской службы.
- [ ] Анализ реестров инженерного оборудования.
- [ ] Интеграция с системой учёта заявок на работы (получение статусов).

Пример условной схемы данных СМВУ — Приложение 1, см. [раздел 6.3](#63-пример-журнала-сработок-приложение-1).

### 2.4. Требования к обработке данных (§7)

**Входные данные**

- [ ] Исторические данные — импорт из файлов CSV / XLSX.
- [ ] Потоковые данные из системы мониторинга СМВУ — интеграция по API / очереди сообщений.
- [ ] Журналы ОДС — загрузка через API.
- [ ] Реестр оборудования — цифровой формат.

Примечание ТЗ: все передаваемые данные должны проходить процедуру обфускации (обезличивания) **на стороне источника**.

**Форматы и способы обмена данными**

- [ ] Файловый обмен: CSV, XLSX.
- [ ] Программный обмен (API): JSON, XML.
- [ ] Взаимодействие с СУБД: поддержка подключения к PostgreSQL (или иной СУБД, используемой в инфраструктуре).
- [ ] Геоданные: GeoJSON, WKT (Well-Known Text).

### 2.5. Производительность и качество прогнозирования (§9)

- [ ] Время формирования прогноза (inference) для одного объекта — не более 5 минут.
- [ ] Время обработки потоковых данных — в режиме, близком к реальному времени (задержка не более 5 минут).
- [ ] Одновременная работа всех пользователей без деградации производительности.
- Целевые показатели точности (Precision) и полноты (Recall) **определяются на этапе проектирования** исходя из качества предоставляемых данных.
- [ ] Горизонт прогнозирования — не менее 24 часов.

### 2.6. Пользовательский интерфейс (§10)

- [ ] **Аналитическая панель (дашборд)** — веб-интерфейс для диспетчеров с визуализацией уровней риска.
- [ ] **Интерактивная карта** — отображение объектов инфраструктуры с выделением проблемных зон.
- [ ] **Журнал прогнозов** — реестр событий с историей прогнозов и результатами их отработки.
- [ ] **Система уведомлений** — оповещение пользователей о критических инцидентах в режиме реального времени.

> 💬 **Прим. команды.** Из сценариев §12 следует ещё одна функция интерфейса: диспетчер **фиксирует решение в системе с выбором причины из справочника**, решение сохраняется в журнале для анализа и дообучения модели. См. [раздел 7](#7-пользовательские-сценарии).

### 2.7. Интеграция (§10)

- [ ] **API-интерфейс** — наличие REST API для получения данных из внешних систем.
- [ ] **Интеграция с системами мониторинга** — получение данных о состоянии оборудования (в режиме чтения).
- [ ] **Синхронизация с базой оборудования** — автоматизированное получение актуальных реестров оборудования из учётных систем Заказчика.

### 2.8. Нефункциональные требования (§11)

**Производительность**

- [ ] Inference для одного объекта — не более 300 секунд.
- [ ] Обработка потоковых данных — близко к реальному времени, задержка не более 300 секунд.
- [ ] Одновременная работа **не менее 20 пользователей** без деградации производительности.

**Надёжность**

- [ ] Доступность системы — в соответствии с регламентом эксплуатации информационных систем Заказчика.
- [ ] Резервное копирование — автоматическое создание резервных копий данных.
- [ ] Восстановление работоспособности после сбоя — не более 4 часов.

**Безопасность**

- [ ] Шифрование данных при передаче — TLS 1.2 и выше.
- [ ] Аутентификация пользователей — поддержка интеграции с корпоративной службой каталогов (LDAP / AD).
- [ ] Разграничение прав доступа на основе ролевой модели (RBAC).
- [ ] Журналирование всех действий пользователей в системе.

**Совместимость и инфраструктура**

- [ ] ОС серверной части — Linux.
- [ ] Браузеры — актуальные версии Google Chrome, Яндекс.Браузер.
- [ ] СУБД — PostgreSQL 12 и выше.

### 2.9. Важные аспекты обработки данных (§13)

- [ ] Интеграция с внутренними системами Заказчика — **исключительно в режиме «только чтение»** (Read-only).
- [ ] Хранение: данные разделяются на **оперативный контур, архивные данные и аналитические витрины**.

### 2.10. Требования к решению (§14)

- [ ] Все необходимые для использования решения методы доступны и подробно описаны.
- [ ] Предоставлен перечень всех использованных библиотек и компонентов.
- [ ] Решение — отдельный сервис, который может стать независимой информационной системой или её компонентом; количество внешних интеграций соответствует целям и задачам.
- [ ] Сложные технические и логические детали решения сопровождаются комментариями.
- [ ] Открытый и неоткомпилированный исходный код, написанный без применения методов обфускации.

**Сопроводительная документация — обязательное условие.** В ней описать:

- [ ] используемые методы обработки данных;
- [ ] условия и ограничения внутри решения;
- [ ] подробные инструкции по компиляции, сборке и установке;
- [ ] функциональную и компонентную архитектуру.

**Нормативные требования.** Использование сервиса и оформление результатов его использования приоритетно должны отвечать требованиям нормативных правовых актов и государственных стандартов из Комплекса стандартов на автоматизированные системы:

- [ ] Федеральный закон от 27.07.2006 № 149-ФЗ «Об информации, информационных технологиях и о защите информации»;
- [ ] Федеральный закон от 27.07.2006 № 152-ФЗ «О персональных данных».

### 2.11. Презентация (§15)

- [ ] Формат pptx или pdf.

### 2.12. UX/UI (§16)

- [ ] Сценарий и путь пользователя интуитивно понятны.

## 3. Побочные задачи

Это не функции сервиса из §4–§14, а то, что **прямо проверяется экспертизой** (§17, §18). Формулировки — из критериев.

- [ ] **Проверка работы расчётов** (§17), реализация прогнозирования и расчётов **сравнением с реальными значениями** (§18).
- [ ] **Оценка достоверности прогнозирования** путём сравнения реальных данных и прогнозных значений (§17, §18).
- [ ] **Проверка рекомендаций сервиса и реальных рекомендаций** в соответствии с реальными условиями (§18).
- [ ] **Реализация дополнительных настраиваемых параметров** (§18).
- [ ] **Объективность диаграмм** — оценивается по их визуальной восприимчивости и отражению данных (§18).
- [ ] **Скорость и удобство работы** (§18), **скорость работы решения** (§17, §18).
- [ ] **Возможность интеграции в любые другие системы** (§17, §18).
- [ ] **Качество кода** (§17, §18).
- [ ] **Выступление на питч-сессии** (§18).

> 💬 **Прим. команды.** Какие именно параметры делать настраиваемыми, ТЗ не уточняет (варианты: пороги риска, горизонт, чувствительность). Ссылка на прототип — не побочная, а обязательная для сдачи (§19).

§8: «реализация данных требований осуществляется по согласованию с Заказчиком в рамках развития функционала сервиса».

**Расширенная аналитика**

- [ ] Детальная статистика по типам инцидентов.
- [ ] Формирование исторических отчётов по ремонтам.
- [ ] Прогнозная аналитика с учётом сезонных изменений.

**Дополнительные модули**

- [ ] Модуль дообучения прогнозных моделей на новых данных.
- [ ] Система формирования рекомендаций по профилактическому обслуживанию.
- [ ] Функционал поддержки формирования черновиков заявок на ремонт (на основе рекомендаций системы).

**Дополнительные интерфейсы**

- [ ] Формирование аналитических отчётов для руководства в различных форматах (PDF, XLSX).

> 💬 **Прим. команды.** В критериях оценки (§17, §18) пункты §8 отдельно не упомянуты — насколько они влияют на баллы, ТЗ не говорит. Не путать с обязательными: сбор решений диспетчера в журнал (§12) и рекомендации по ТО на основе состояния оборудования (§4, §6) — обязательны; **модуль дообучения** и **система рекомендаций по профилактическому обслуживанию** — по согласованию.

## 5. Что сервис НЕ должен делать

**Прямо в ТЗ** (§5). Сервис НЕ должен:

- ❌ замещать работу диспетчеров;
- ❌ принимать окончательные решения об инцидентах;
- ❌ управлять инженерным оборудованием напрямую;
- ❌ проводить ремонтные работы.

**Прямо в ТЗ, запреты из других разделов:**

- ❌ Интегрироваться с внутренними системами Заказчика иначе чем в режиме «только чтение» (§13; для систем мониторинга — «в режиме чтения», §10).
- ❌ Применять обфускацию к исходному коду и сдавать скомпилированный код (§14).

> 💬 **Прим. команды.** Из §5 и §12 следует: окончательное решение фиксирует диспетчер, сервис даёт вероятность, горизонт, локацию и рекомендацию. Из §7 и 152-ФЗ следует: данные приходят обезличенными, раскрывать персональные данные нельзя. Из §16: не выводить на экран элементы, которые не нужны для задач пользователя.

## 6. Данные

### 6.1. Внутренние источники (§13)

| Источник | Содержимое | Режим / глубина |
|---|---|---|
| **Система СМВУ** | данные с датчиков: контактные, объёмные, температурные, дымовые, газовые | интеграция в режиме, близком к реальному времени (near real-time) |
| **Журналы ОДС** | записи о срабатываниях, история инцидентов | глубина данных — не менее 12 лет |

## 7. Пользовательские сценарии (§12)

ТЗ приводит их как **пример** пользовательского сценария.

### 7.1. Прогнозирование пожара в инженерном коллекторе

**Участники:** диспетчер (основной пользователь); аналитик (ответственный за верификацию данных).

**Предпосылки:** в системе накоплены исторические данные об инцидентах; система интегрирована с датчиками мониторинга и реестром плановых работ.

1. **Анализ данных** — система в автоматическом режиме сопоставляет текущие показания датчиков (температура, задымление) с данными о плановых работах и историческими паттернами.
2. **Формирование прогноза** — при выявлении аномалий система рассчитывает вероятность инцидента и формирует предупреждение.
3. **Уведомление** — диспетчер получает уведомление на дашборд с указанием вероятности, временного горизонта и локации объекта.
4. **Верификация** — диспетчер анализирует данные, при необходимости использует внешние источники (например, камеры наблюдения) для подтверждения ситуации.
5. **Принятие решения** — диспетчер фиксирует решение в системе (например, «выезд бригады» или «ложное срабатывание») с выбором причины из справочника.
6. **Завершение** — информация о принятом решении сохраняется в журнале для последующего анализа и дообучения модели.

### 7.2. Прогнозирование инцидента (подтопление)

**Участники:** диспетчер (основной пользователь); аналитик (ответственный за верификацию данных).

**Предпосылки:** в системе накоплены исторические данные о подтоплениях; система интегрирована с датчиками мониторинга и внешними источниками метеоданных.

1. **Анализ данных** — система в автоматическом режиме сопоставляет данные о частоте включения насосных станций с прогнозом метеослужб и историческими паттернами подтоплений.
2. **Формирование прогноза** — при выявлении аномалий система рассчитывает вероятность инцидента и формирует предупреждение.
3. **Уведомление** — диспетчер получает уведомление на дашборд с указанием вероятности, временного горизонта и локации объекта.
4. **Верификация** — диспетчер анализирует данные, при необходимости использует внешние источники (например, камеры наблюдения) для подтверждения ситуации.
5. **Принятие решения** — диспетчер фиксирует решение в системе (например, «направление бригады на проверку» или «мониторинг ситуации») с выбором причины из справочника.
6. **Завершение** — информация о принятом решении сохраняется в журнале для последующего анализа и дообучения модели.

**Результат:**

- своевременное информирование диспетчера о рисках подтопления;
- фиксация принятых мер в системе;
- накопление данных для повышения точности будущих прогнозов.

## 10. Открытые вопросы и противоречия

> 💬 Весь раздел — **прим. команды**: что ТЗ не определяет или определяет по-разному.

**Противоречия и дубли**

- **Число пользователей:** §9 — «одновременная работа всех пользователей», §11 — «не менее 20 пользователей».
- **Время прогноза и задержка потока:** §9 — 5 минут, §11 — 300 секунд. Значения совпадают, требование продублировано.
- **Точность:** §5 — «точность прогнозов не ниже установленных показателей», §9 — показатели Precision / Recall «определяются на этапе проектирования». Конкретных цифр в ТЗ нет.
- **Рекомендации:** «рекомендации по ТО на основе данных о состоянии оборудования» — обязательны (§4, §6); «система формирования рекомендаций по профилактическому обслуживанию» — по согласованию (§8). Граница между ними не описана.
- **Заявки:** интеграция с системой учёта заявок (получение статусов) — обязательна (§6); черновики заявок на ремонт — по согласованию (§8).

**Не определено**

- **Параметры, оставленные Заказчику или проектированию:** доступность системы (по регламенту Заказчика, §11); СУБД — PostgreSQL или иная из инфраструктуры (§7), при этом §11 требует PostgreSQL 12+.
- **Реальные данные** — в ТЗ только условная схема (Приложение 1).
- **Типы каналов:** в Приложении 1 кроме датчиков есть насос, вентилятор, фаза, переключатель; в §13 для СМВУ перечислены только контактные, объёмные, температурные, дымовые, газовые датчики.
- **СКУД** есть в терминах, но не указан среди источников данных, хотя §4 требует поддержки при верификации несанкционированного доступа.
- **Камеры наблюдения** в сценариях — внешний источник для диспетчера; интеграция с ними в требованиях не указана.
- **Реестр плановых работ** — в предпосылках сценария пожара (§12), но в источниках §13 отдельно не назван.
- **Аналитик** — участник сценариев (§12), но не входит в основных пользователей (§3).
- **Критический инцидент** определён в терминах как «событие, угрожающее жизни человека»; уведомления в реальном времени требуются именно о критических инцидентах (§10).
- **Пикет** определён в терминах («участок работ»), но в тексте ТЗ не используется.
