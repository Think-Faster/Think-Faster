## Коротко

Снаружи открыт один nginx: он держит TLS и по суффиксу URL разводит запросы на фронт и на четыре сервиса. Внутри контура всё ходит по обычному HTTP, но каждый сервис первым делом проверяет подпись JWT — своего публичного ключа ему для этого хватает, в сервис аутентификации он больше не ходит. Субъектом запроса бывает живой пользователь или техническая учётка сервиса. Данные лежат в двух контейнерах PostgreSQL: отдельный под аудит и общий с четырьмя схемами; рабочие контейнеры ходят туда под учёткой на чтение-запись, миграции прогоняет отдельный контейнер под административной.

## 1. Периметр и маршрутизация

Два nginx, и это разные роли:

| | роль |
|---|---|
| **nginx-фронт** | отдаёт статику собранного React |
| **nginx reverse proxy** | единственная точка входа снаружи: порты 80 и 443, редирект 80 → 443, TLS |

Reverse proxy смотрит на суффикс URL. Суффикса нет — это фронт. Есть `/api` — это бэкенд, и дальше по конкретному суффиксу:

| маршрут | сервис |
|---|---|
| `/` | статика фронта |
| `/api/bff` | BFF |
| `/api/dispatch` | Dispatch |
| `/api/funnel` | Funnel |
| `/api/ml` | ML |

Домен в примере — `tf.ru`. Настройка маршрутизации — «типа три строки в Nginx» (запись 1, 03:21).

## 2. Аутентификация: JWT и ключи

У BFF есть «отросток» — сервис аутентификации. Механика:

1. При запуске выпускается пара ключей X.509 — приватный и публичный.
2. Пользователь вводит логин и пароль → генерируется пара токенов: **токен доступа на 10 минут** и **токен обновления на сутки**.
3. Токен подписывается приватным ключом и отдаётся клиенту; во фронте он ложится в куки (это происходит автоматически).
4. У сервиса аутентификации есть API-ручка, отдающая публичный ключ. Остальные сервисы забирают его **один раз при старте** — постоянного обмена между ними нет.
5. Протух токен доступа, но жив токен обновления — клиент идёт в сервис аутентификации и получает новый.

В базе сервиса аутентификации хранятся **только логин и хэш пароля**. Токены не хранятся: срок жизни зашит внутрь токена, после него это бесполезная строка.

Из второй записи, про стойкость: JWT пишется в Base64, длинный, со спецсимволами; перебором его не взять — «надо 70 лет рассчитывать на квантовом компьютере» (запись 2, 09:18). Сертификат, которым подписываются токены, имеет срок действия и перевыпускается раз в год.

## 3. Авторизация: RBAC сейчас, ABAC — задел

- **RBAC** — роль на действие, на неё и завязываемся. Группа — это строка в базе со списком пользователей, группы работают как роли.
- **ABAC** — права по атрибуту объекта: у датчика появляется владелец (колонки с ид групп и их правами в таблице датчиков). По текущей схеме данных не предусмотрен, но переключить на него можно будет позже.

Права доступа к заявкам регулируются RBAC (запись 2, 03:10).

## 4. Проверка токена в каждом сервисе

Модуль безопасности внедряется во все микросервисы, включая почтовые уведомления и телеграм. Любой запрос в любой сервис сначала проверяет токен, и только потом выполняется: берётся подпись, пришедшая вместе с токеном, и проверяется публичным ключом. Публичный ключ секрета не составляет.

Смысл закрывать токеном даже уведомления: иначе адрес ручки узнают снаружи и начнут слать через неё что угодно.

## 5. Технические учётные записи

В токене есть `sub` — идентификатор субъекта, который отправил запрос. Субъекта два вида: живой пользователь и техническая учётная запись.

- Своя техучётка — у каждого сервиса, который ходит в соседние: dispatch, bff, почта.
- Тому, кто сам никуда не ходит, учётка не нужна.
- Токены техучёток выпускаются надолго — «на год примерно, по стандарту» (запись 2, 07:23).
- Права техучёток между собой ещё предстоит разграничить — доступ ко всем командам API им не нужен.

## 6. Приём данных с датчиков

Подделать сырые показания через наш API не выйдет: датчики тоже приходят с токеном. Закрывать доступ по IP каждого датчика бессмысленно — в одном помещении их под три сотни, «мы уже на десятом датчике скажем, нет, это херня» (запись 2, 06:42).

Поэтому шина данных — на стороне объекта: их сервис собирает показания датчиков, пропускает через себя и ходит к нам с одного статического IP. Ему выдаётся долгий токен, а проверяет этот токен **сервис-воронка** (`/api/funnel`).

## 7. Заявки и уведомления

- Алерт с датчика или расчёт ML приходит в dispatch, dispatch отдаёт в BFF, где складывается информация о событии. Единица работы — **заявка**.
- Кто первым взял заявку в работу, тот её и ведёт.
- Уведомление уходит **всей группе адресатов** — на почту и в телеграм-бот.
- Разослать «только тем, кто на смене» нельзя: токены в системе не хранятся, значит, узнать, кто сейчас авторизован, неоткуда.
- Сессии вместо токенов рассматривались и отклонены: сервис аутентификации перестал бы быть тонким местом с ровной нагрузкой и стал бы проверять каждый запрос; к тому же сессия закрывает фронт, а для микросервиса всё равно нужен токен.
- Идея на будущее: завести в BFF рабочее расписание и определять смену по графику.

## 8. Аудит

Отдельный сервис, вспомнили по ходу первой записи — он есть в требованиях. Собирает логи всех сервисов: какой запрос пришёл, куда, от кого. Может фиксировать и протухшие токены, но их будет много: токен живёт 10 минут. База — своя, в отдельном контейнере, в идеале вообще на другой машине.

## 9. База данных

Два контейнера PostgreSQL:

| контейнер | содержимое |
|---|---|
| первый | только журнал аудита |
| второй | всё остальное — четыре схемы, по одной на сервис |

Внутри схемы — таблицы. Пользователи и группы самой базы — отдельная сущность, они **не равны** пользователям системы: пользователь системы это запись в таблице `users` (логин, почта, пароль), пользователь базы живёт в системных таблицах PostgreSQL.

Права в базе трёх видов: чтение, запись и администрирование. Администрирование позволяет создавать таблицы. Все, кто ходит в базу за данными, получают RW-группу.

## 10. Контейнеры сервисов и миграции

У сервиса два докер-контейнера:

- **рабочий** — запущен всегда, работает под RW-учёткой;
- **конфигурационный** — запускается вручную, прогоняет миграцию под административной учёткой и выключается.

Миграция генерирует SQL (`create table` и список полей) по классам в коде, чтобы не заводить таблицы руками и не ошибиться в названии поля.
