## Зачем

Сдаём прототип ссылкой на работающий стенд ([ТЗ, раздел 9](../docs/ТЗ.md)). Значит, площадка — не фон, а часть результата: если она ляжет 29-го, ляжет вся сдача.

Сейчас про Yandex Cloud известно только то, что есть грант для команд на SourceCraft ([docs/SourceCraft.md](../docs/SourceCraft.md)). Не известно главное: **чей аккаунт, сколько там денег и на сколько их хватит** при нашем стеке. Это надо посчитать до того, как Гриша начнёт разворачивать, а не после.

Вторая часть — документация. Команда из пяти человек, доступ к стенду нужен всем, и «спроси у Сани» не масштабируется даже на две недели.

## Что сделать

### 1. Что у нас есть на самом деле

- [ ] Статус заявки на грант: подана, одобрена, сколько начислено, до какого числа действует.
- [ ] **Чей платёжный аккаунт** — личный, командный, кто владелец. Записать, потому что от этого зависит, кто сможет чинить стенд в ночь перед сдачей.
- [ ] Что происходит при исчерпании гранта: ресурсы останавливаются или списывается с карты. Проверить и записать явно — это риск потерять стенд в последний день.
- [ ] Каталог (folder) и облако: одно на команду, названия зафиксировать.
- [ ] Ограничения пробного и грантового режима: квоты на vCPU, RAM, диски, публичные IP.

### 2. Разбор сервисов под наш стек

Для каждого слоя из [плана](plan.md) — что берём в облаке и почему. Выбор из двух подходов: **всё на одной виртуалке в Docker Compose** или **управляемые сервисы**.

- [ ] Таблица сравнения, заполнить цифрами, а не ощущениями:

| Слой | Вариант «одна ВМ» | Вариант «управляемый сервис» | Что берём |
|---|---|---|---|
| PostgreSQL 16 | контейнер на ВМ | Managed Service for PostgreSQL | |
| Redis | контейнер на ВМ | Managed Service for Redis | |
| Бэкенд + фронт | Docker Compose на ВМ | Serverless Containers | |
| Файлы, Parquet, бэкапы | диск ВМ | Object Storage | |
| Обучение модели | на ВМ | DataSphere | |
| Реестр образов | — | Container Registry | |

- [ ] По каждой строке — **ориентировочная цена в месяц** и в пересчёте на 13 дней проекта.
- [ ] Прикинуть нагрузку по нашим цифрам: 313,5 млн строк истории, рост ~4–5 млн строк в месяц, 20 одновременных пользователей, задержка потока ≤ 5 минут ([ТЗ, разделы 2.5 и 2.8](../docs/ТЗ.md)). Отсюда — минимально достаточная конфигурация ВМ и размер диска.
- [ ] Отдельно посчитать, **влезает ли полная история** в грант, или в облако кладём только 2025–2026, а остальное держим локально в DuckDB.
- [ ] **Решение с обоснованием** — и сразу запись `D-003` в [decision.md](../decision.md) в формате из [TF-6](TF-6.md).

### 3. Сеть, доступы и безопасность

- [ ] Схема стенда: что в публичной сети, что во внутренней. Наружу смотрит только nginx, всё остальное — во внутренней сети ([TF-5](TF-5.md), записка о потоке).
- [ ] Группы безопасности: какие порты открыты и откуда. По умолчанию закрыто всё, кроме 443 и SSH по ключу.
- [ ] **TLS 1.2+** обязателен по ТЗ ([раздел 2.8](../docs/ТЗ.md)): как получаем сертификат — Certificate Manager или Let's Encrypt, нужен ли домен и чей.
- [ ] Учётные записи: персональные, вход по SSH-ключам, без общего `user1` (это же требование в [TF-4](TF-4.md)). Кто администратор облака, у кого только доступ к ВМ.
- [ ] **Секреты**: где лежат ключи и пароли. В репозитории только `.env.example`. Проверить, что ни один ключ не попал в git, в том числе в историю.
- [ ] Резервное копирование ([ТЗ, раздел 2.8](../docs/ТЗ.md) требует автоматических копий и восстановления не дольше 4 часов): что копируем, куда, как часто, **и проверить восстановление хотя бы один раз** — невосстановленный бэкап бэкапом не считается.

### 4. Документация для работы

Три коротких документа. Критерий один: человек из команды делает по ним всё сам, не спрашивая меня.

**4.1. `docs/infra/yandex-cloud.md` — что где лежит**

- [ ] Схема стенда одной картинкой (Mermaid): ВМ, сервисы, сети, что наружу.
- [ ] Таблица ресурсов: имя, тип, конфигурация, для чего, цена в месяц.
- [ ] Кто владелец аккаунта, у кого какие права.
- [ ] Лимиты и что делать при их исчерпании.

**4.2. `docs/instructions/доступ-и-деплой.md` — как работать**

- [ ] Как получить доступ: что прислать мне, что я выдам в ответ.
- [ ] Как подключиться по SSH, как посмотреть логи, как перезапустить сервис.
- [ ] Как выкатить изменения: от коммита до работающего стенда, по шагам, с командами.
- [ ] Как откатиться, если выкатили сломанное.
- [ ] Что делать **нельзя**: удалять ресурсы, менять группы безопасности, класть секреты в репозиторий, выкатывать напрямую в день сдачи без проверки.

**4.3. `docs/instructions/стенд-упал.md` — короткая инструкция на случай ЧП**

- [ ] Пять типовых поломок и что нажать: сервис не отвечает, кончилось место, кончился грант, не работает база, не пускает по SSH.
- [ ] Кому звонить и в каком порядке.
- [ ] Держать на одной странице — в панике длинное не читают.

### 5. План Б

- [ ] Что делаем, если грант не дадут или он кончится 27-го числа: сервер Гриши из [TF-4](TF-4.md), локальный запуск по Docker Compose, демо с ноутбука.
- [ ] Условие переключения — назвать датой и признаком: «если к 24.09 стенд не отвечает стабильно, демо готовим локально».
- [ ] Проверить, что проект **поднимается одной командой из чистого клона** независимо от облака. Это и есть настоящая страховка.

## Готово, когда

- [ ] Известно, чей аккаунт, сколько денег и до какого числа.
- [ ] Выбор «ВМ или управляемые сервисы» сделан и посчитан в рублях, записан в `decision.md`.
- [ ] Гриша разворачивает сервис по инструкции, ни о чём не спрашивая.
- [ ] Наружу открыт только 443, сертификат выдан, `https://` открывается.
- [ ] Бэкап снят **и восстановлен** хотя бы раз.
- [ ] Проект поднимается из чистого клона одной командой без облака.

## Не входит в задачу

- Настройка самих сервисов и написание Compose-файлов — [TF-4](TF-4.md), Гриша.

- Реальная интеграция с LDAP / AD.
- Перенос репозитория из GitHub: [решено](plan.md) — код на GitHub, сервер в Yandex Cloud.
