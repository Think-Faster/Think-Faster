## Зачем

Сервис должен прогнозировать отказы и инциденты и отличать реальные срабатывания от ложных ([ТЗ, разделы 1–2](../docs/ТЗ.md)). Прежде чем строить что-то на данных, нужно знать:

- что в данных **шум**, а что **реальное событие**;
- как выглядели **реальные поломки** — это эталон, на котором потом проверяются прогнозы (критерии оценки: «сравнение реальных данных и прогнозных значений», [ТЗ, раздел 8](../docs/ТЗ.md#8-критерии-оценки));
- единый **справочник датчиков** с ID и порогами — чтобы бэкенд и алгоритмы говорили на одном языке.

Схема данных из ТЗ: [Приложение 1](../docs/ТЗ.md#63-пример-журнала-сработок-приложение-1).

## Что сделать

### 1. Обзор данных — наличие и деградация

- [ ] Период данных по каждому источнику: первая и последняя дата.
- [ ] Объём по годам: число записей, число активных каналов.
- [ ] Каналы по типам (температура, дым, движение, газ, насос, вентилятор, фаза, контакт, переключатель).
- [ ] **Деградация**: доля пропусков по годам, годы или периоды, где данных мало или нет, каналы, которые «замолчали».
- [ ] Вывод одной фразой: за какой период данным можно доверять.

### 2. Шумы — самое важное

Для каждого вида шума заполнить карточку:

| Поле | Что писать |
|---|---|
| Название | короткое, одно на всю команду |
| Определение | одной фразой |
| Правило обнаружения | условие, которое можно запрограммировать: пороги, окна времени |
| Пример | ИД канала, время, значения |
| Масштаб | сколько случаев, доля от всех записей, на каких типах каналов |
| Как отличить от реального события | признаки |
| Что с ним делать | пометить / сгладить / исключить из обучения |

Проверить как минимум эти виды — подтвердить или опровергнуть на данных:

- [ ] **Дребезг** — много переключений состояния за короткое время.
- [ ] **Выброс** — одиночный скачок значения и возврат обратно.
- [ ] **Залипание** — значение не меняется неестественно долго.
- [ ] **Пропуски связи** — канал перестал писать.
- [ ] **Дубли** — одинаковые записи.
- [ ] **Физически невозможные значения** — например, температура вне реального диапазона.
- [ ] **Ложное срабатывание** — тревога, которая сама вернулась в норму без подтверждённого инцидента.
- [ ] Любые другие виды, найденные в данных.

> ⚠️ Данные в БД **не менять и не удалять** — только читать и помечать в своих выгрузках. Интеграция только в режиме чтения ([ТЗ, раздел 2.9](../docs/ТЗ.md)).

### 3. Прецеденты поломок

- [ ] Определить, по какому признаку в данных видна **реальная** поломка или авария (тип записи в журнале, статус, подтверждение).
- [ ] Отобрать прецеденты: **не меньше 10** или все, если их меньше. Покрыть все типы, которые есть в данных: отказ датчика, отказ оборудования, пожар, подтопление, проникновение. Если какого-то типа нет — прямо написать об этом.
- [ ] Для каждого прецедента — карточка:

| Поле | Что писать |
|---|---|
| ID прецедента | `P-01`, `P-02`, … |
| Дата и время | |
| Объект | тег `МК-…`, объект из дерева, система |
| Тип | отказ датчика / отказ оборудования / пожар / подтопление / проникновение / другое |
| Каналы | ИД и типы каналов, участвовавших в событии |
| **Что было за 24 ч до** | как менялись показания: есть ли предвестники. Горизонт прогноза по ТЗ — не менее 24 ч |
| Как зафиксировано | запись в журнале, чем закончилось |
| Вывод | можно ли было это предсказать и по каким признакам |

### 4. Справочник датчиков — для встраивания

- [ ] Таблица по **типам каналов**:

| Поле | Пример |
|---|---|
| `channel_type_id` | 12 |
| `name` | temperature |
| `dispatcher_name` | Температура |
| `unit` | °C |
| `normal_min` / `normal_max` | диапазон нормы |
| `warning_threshold` | порог предупреждения |
| `alarm_threshold` | порог аварии |
| `threshold_source` | журнал / уставка в БД / статистика / регламент |
| `channels_count` | число каналов этого типа |
| `comment` | особенности: дискретный 0/1, направление порога и т. п. |

- [ ] Если у отдельных каналов пороги отличаются от типа — отдельная таблица исключений по `channel_id`.
- [ ] Названия полей и ID — **ровно как в БД**, чтобы бэкенд подгрузил без переименований.
- [ ] Для дискретных каналов (дым, движение, контакт) вместо порога описать, какое состояние аварийное.
- [ ] Сверить пороги с результатом алгоритма Захара (TF-3): где расходятся — записать.

### 5. Открытые вопросы

- [ ] Всё, что не удалось понять из данных, — списком в конце обзора: что неясно, что проверял, у кого можно спросить.

## Готово, когда

- [ ] У каждого вида шума есть правило, пример и масштаб.
- [ ] Прецедентов не меньше 10 (или все имеющиеся), у каждого заполнено «что было за 24 ч до».
- [ ] CSV открывается, ID совпадают с БД.
- [ ] Захар и Гриша могут пользоваться справочником, не задавая вопросов.
- [ ] Расчёты воспроизводятся из приложенных запросов.
