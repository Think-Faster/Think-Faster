## Зачем

Сервис должен прогнозировать отказы и инциденты и отличать реальные срабатывания от ложных ([ТЗ, разделы 1–2](../docs/ТЗ.md)). Прежде чем строить что-то на данных, нужно знать:

- **как устроены данные** — какие файлы, поля, связи, чему в них можно доверять;
- что в данных **шум**, а что **реальное событие**;
- как выглядели **реальные поломки** — это эталон, на котором потом проверяются прогнозы (критерии оценки: «сравнение реальных данных и прогнозных значений», [ТЗ, раздел 8](../docs/ТЗ.md#8-критерии-оценки));
- единый **справочник датчиков** с ID и порогами — чтобы бэкенд и алгоритмы говорили на одном языке.

Схема данных из ТЗ: [Приложение 1](../docs/ТЗ.md#63-пример-журнала-сработок-приложение-1).

## Разделение с TF-3

| Гера (TF-1) | Захар (TF-3) |
|---|---|
| **Что** данные значат: структура, шум, поломки, нормы | **Считает** по этим описаниям: пороги, классификация, отсев шума |
| Описывает правило шума словами и примером | Программирует правило и гоняет по всей истории |
| Говорит, какие пороги верные и откуда взяты | Сопоставляет показания с порогом, выдаёт группы A, B, C |

Захар не разбирает данные заново — он берёт твои документы. Поэтому **шаги 1 и 5 нужны ему раньше остальных**.

> ⚠️ Данные **только читать**. Ничего не менять и не удалять, пометки — в своих выгрузках ([ТЗ, раздел 2.9](../docs/ТЗ.md)).

## Что сделать

### 1. Структура данных и связи

- [ ] Файлы и таблицы: период данных, число строк, число каналов — сверить с [описанием](../docs/dataset/описание.md#объём-по-годам).
- [ ] Для каждой таблицы — поля:

| Поле | Тип | Смысл | Пример | Доля пустых | Ключ |
|---|---|---|---|---|---|

- [ ] Связи — списком «таблица.поле → таблица.поле». Отдельно: **связи «канал → объект» в данных нет** ([описание](../docs/dataset/описание.md)) — восстановить по названиям и пикетам. Организаторы дополнили датасет — файл будет у капитана; если связи нет и там, сопоставляем сами и описываем правило.
- [ ] Проверка целостности, с количеством: записи журнала с каналом, которого нет в реестре; каналы без единой записи; дубли ID. Рабочий ключ записи — предложить и обосновать.
- [ ] Расшифровка тега `<префикс>-a.b.c.d.`: что означает каждый уровень. В [описании](../docs/dataset/описание.md#тег) есть гипотеза — подтвердить или опровергнуть.
- [ ] **ER-диаграммы по случаям**: аварийное событие и **что параллельно с ним происходит** — какие ещё каналы и записи того же объекта (и соседних по тегу) попадают в то же окно времени. Не меньше 3 случаев; три готовых образца — в [анализе](../docs/dataset/анализ.md). Формат — Mermaid, GitHub рисует его прямо в `.md`.

### 2. Как хранятся значения

- [ ] Аналоговые (температура, газ) и дискретные (дым, движение, контакт) — как различаются в одном поле `значение_датчика`.
- [ ] Частота записи: периодически или только при изменении. По типам каналов.
- [ ] Формат даты, часовой пояс, десятичный разделитель (в журналах точка, в ТЗ `25,00` — запятая).
- [ ] **Где фиксируется авария**: флаг `тревожное`, состояние в значении, или и то и другое — и насколько они согласованы.
- [ ] Есть ли в данных уставки — пороговые значения каналов. Если нет — так и написать.

### 3. Обзор данных — наличие и деградация

- [ ] Объём по годам: число записей, активных каналов, тревожных строк.
- [ ] Каналы по типам (температура, дым, движение, газ, насос, вентилятор, фаза, контакт, переключатель).
- [ ] **Деградация**: доля пропусков по годам, периоды, где данных мало или нет, каналы, которые «замолчали».
- [ ] Вывод одной фразой: за какой период данным можно доверять и что исключить из обучения.

### 4. Шумы — самое важное

Для каждого вида шума заполнить карточку:

| Поле | Что писать |
|---|---|
| Название | короткое, одно на всю команду |
| Определение | одной фразой |
| Правило обнаружения | условие, которое Захар сможет запрограммировать: пороги, окна времени |
| Пример | ИД канала, время, значения |
| Масштаб | сколько случаев, доля от всех записей, на каких типах каналов |
| Как отличить от реального события | признаки |
| Что с ним делать | пометить / сгладить / исключить из обучения |

Проверить как минимум эти виды — подтвердить или опровергнуть на данных:

- [ ] **Дребезг** — много переключений состояния за короткое время.
- [ ] **Выброс** — одиночный скачок значения и возврат обратно.
- [ ] **Залипание** — значение не меняется неестественно долго.
- [ ] **Пропуски связи** — канал перестал писать.
- [ ] **Дубли** — одинаковые записи.
- [ ] **Физически невозможные значения** — например, температура вне реального диапазона.
- [ ] **Ложное срабатывание** — тревога, которая сама вернулась в норму без подтверждённого инцидента.
- [ ] Кандидаты Н1–Н9 из [анализа](../docs/dataset/анализ.md#кандидаты-в-шум) — довести до карточек или отклонить.

### 5. Справочник датчиков — для встраивания

- [ ] Таблица по **типам каналов**:

| Поле | Пример |
|---|---|
| `channel_type_id` | 12 |
| `name` | temperature |
| `dispatcher_name` | Температура |
| `unit` | °C |
| `normal_min` / `normal_max` | диапазон нормы |
| `warning_threshold` | порог предупреждения |
| `alarm_threshold` | порог аварии |
| `threshold_source` | журнал / уставка / статистика / регламент |
| `channels_count` | число каналов этого типа |
| `comment` | особенности: дискретный, направление порога и т. п. |

- [ ] Если у отдельных каналов пороги отличаются от типа — отдельная таблица исключений по `channel_id`.
- [ ] Названия полей и ID — **ровно как в данных**, чтобы бэкенд подгрузил без переименований.
- [ ] Для дискретных каналов (дым, движение, контакт) вместо порога описать, какое состояние аварийное.
- [ ] **Направление порога**: не у всех каналов авария — это «выше». Указать явно.

📌 **К 13:00 — отдать Захару шаг 1 и черновик шага 5.** Дальше он считает, ты продолжаешь шаги 3, 4, 6.

### 6. Прецеденты поломок

- [ ] Определить, по какому признаку в данных видна **реальная** поломка или авария. Подтверждений диспетчера в данных нет — отбирать через параллельные события ([анализ](../docs/dataset/анализ.md)).
- [ ] Отобрать прецеденты: **не меньше 10** или все, если их меньше. Покрыть все типы, которые есть в данных: отказ датчика, отказ оборудования, пожар, подтопление, проникновение. Если какого-то типа нет — прямо написать об этом.
- [ ] Для каждого прецедента — карточка:

| Поле | Что писать |
|---|---|
| ID прецедента | `P-01`, `P-02`, … |
| Дата и время | |
| Объект | тег, объект из дерева, система |
| Тип | отказ датчика / отказ оборудования / пожар / подтопление / проникновение / другое |
| Каналы | ИД и типы каналов, участвовавших в событии |
| **Что было за 24 ч до** | как менялись показания: есть ли предвестники. Горизонт прогноза по ТЗ — не менее 24 ч |
| **Что происходило параллельно** | другие каналы и события того же объекта и соседних в то же время — с ER-диаграммой из шага 1 |
| Как зафиксировано | запись в журнале, чем закончилось |
| Вывод | можно ли было это предсказать и по каким признакам |

### 7. Открытые вопросы

- [ ] Всё, что не удалось понять из данных, — списком: что неясно, что проверял, у кого можно спросить. Начало списка — в конце [анализа](../docs/dataset/анализ.md).

## Готово, когда

- [ ] Захар и Гриша понимают структуру данных по документу без вопросов к Гере.
- [ ] Есть схема связей, ER-диаграммы случаев с параллельными событиями и проверка целостности с цифрами.
- [ ] У каждого вида шума есть правило, пример и масштаб — правило можно запрограммировать, не переспрашивая.
- [ ] Прецедентов не меньше 10 (или все имеющиеся), у каждого заполнено «что было за 24 ч до».
- [ ] CSV открывается, ID совпадают с данными.
- [ ] Расчёты воспроизводятся из приложенных запросов.
