## Зачем

Алгоритм превышений — первый **детерминированный** расчёт на реальных данных. Он показывает, где показания и журнал аварий согласуются, а где нет. Расхождения — прямой материал для поиска шума и ложных срабатываний.

Отсев шума — вторая половина: Гера описывает виды шума словами и примерами, ты превращаешь описания в код и прогоняешь по всей истории. Без этого модель будет учиться на дребезге.

## Разделение с TF-1

| Гера (TF-1) | Захар (TF-3) |

| Какие пороги верные и откуда взяты | Сопоставление показаний с порогом, группы A, B, C |

Структуру данных заново не разбирать — брать у Геры ([TF-1, шаг 1](TF-1.md)). Пока черновика нет, работать по [docs/dataset/](../docs/dataset/): [описание.md](../docs/dataset/описание.md) — формат и поля, [анализ.md](../docs/dataset/анализ.md) — что уже известно про пороги и шум, [запросы.sql](../docs/dataset/запросы.sql) — готовые запросы к DuckDB.

## Что сделать

### 1. Подготовка

- [ ] Поднять данные у себя: DuckDB по инструкции из [описания](../docs/dataset/описание.md#как-распаковать-и-загрузить), ссылка на архивы там же.
- [ ] Прочитать черновик Геры. Что непонятно — спросить сразу, не додумывать.
- [ ] Зафиксировать рабочий ключ записи и период, на котором считаем (по выводу Геры о деградации).

### 2. Алгоритм превышения аварийных порогов

**Идея:** определить аварийный порог по тому, при каких значениях журнал фиксирует аварию, и сравнить все показания с этим порогом.

- [ ] **Порог.** Для каждого типа канала (и для отдельных каналов, если отличаются):
  - если у Геры есть уставка или обоснованный порог — брать его;
  - если нет — вывести из журнала: значение показания в момент аварийной записи; как агрегировать (минимум, медиана), зафиксировать и обосновать.
- [ ] **Сопоставление.** Аварийная запись ↔ показание канала: по ИД канала и времени в окне ± N минут. Окно — параметр.
- [ ] **Классификация.** Каждый случай отнести к одной из групп:

| Группа | Условие | Что это может значить |
|---|---|---|
| A. Подтверждённые | значение выше порога **и** есть аварийная запись | реальная авария |
| B. Без записи | значение выше порога, аварийной записи **нет** | пропуск в журнале или выброс |
| C. Запись без превышения | аварийная запись есть, значение **ниже** порога | кандидат в шум или ложное срабатывание |

- [ ] **Направление порога.** Не у всех каналов авария — это «выше»: учесть нижние пороги и дискретные каналы (для них превышение — переход в аварийное состояние).
- [ ] **Параметры** запуска: тип канала, период, окно сопоставления.
- [ ] **Реализация** — SQL-запрос или Python-скрипт, только чтение.
- [ ] **Пробный прогон**: температура за 1 месяц → количество случаев в группах A, B, C и по 3–5 примеров в каждой. Затем газ — по нему порог уже нащупан ([анализ](../docs/dataset/анализ.md)).

### 3. Отсев шума

- [ ] Взять карточки шумов из [TF-1, шаг 4](TF-1.md) и реализовать правила: дребезг, выброс, залипание, пропуски связи, дубли, невозможные значения.
- [ ] Каждое правило — отдельная функция или запрос с параметрами (окно, порог срабатываний), чтобы можно было крутить, не переписывая код.
- [ ] Прогнать по всей истории: сколько записей помечает каждое правило, доля от всех, на каких типах каналов.
- [ ] **Ничего не удалять** — только проставлять метку в своей выгрузке: `noise_rule`, `noise_score` или аналог.
- [ ] Сверить с масштабом, который заявил Гера. Расхождения больше чем в разы — разобрать вместе, не подгонять.

### 4. Передать команде

- [ ] Гере: таблицу порогов и списки групп B и C — для сверки со справочником датчиков и отбора прецедентов.
- [ ] Грише: формат выдачи алгоритма — какие поля вернёт API ([TF-4](TF-4.md), `/api/v1/thresholds`).
