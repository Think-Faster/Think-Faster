## Зачем

ТЗ требует не просто прогноз, а **встраиваемый** сервис: REST API для получения данных из внешних систем, чтение чужих баз только в режиме Read-only, разделение хранения на оперативный контур, архив и аналитические витрины ([ТЗ, разделы 2.7 и 2.9](../docs/ТЗ.md)). Отдельный критерий финальной экспертизы — **возможность интеграции в любые другие системы** ([ТЗ, раздел 8](../docs/ТЗ.md)). Это баллы, которые берутся документацией, а не кодом.

Второй кусок — техработы. Заметная часть тревог в журнале похожа на обслуживание: пачки событий в рабочее время, снятие с охраны, двери, движение. Если не отделить их от инцидентов, модель будет учиться на действиях бригады. Но глушить всё подряд нельзя: пока люди внизу, газ и дым важнее, чем когда-либо.

## Что сделать

### 1. Документация: как пользоваться нашей БД и как встроить внешнюю систему

Два адресата — два раздела в одном документе.

**1.1. Для того, кто читает наши данные**

- [ ] Схема хранения тремя контурами ([ТЗ, раздел 2.9](../docs/ТЗ.md)): что лежит в оперативном контуре (последние показания и открытые прогнозы), что в архиве (вся история с 2019), что в витринах (агрегаты для дашборда). Для каждой таблицы — назначение одной фразой.
- [ ] Словарь полей: имя, тип, смысл, единица, пример, допустимые значения. Имена — **ровно как в БД**, без перевода.
- [ ] Ключи и связи: чем джойнить канал с объектом, событие с каналом, прогноз с событием.
- [ ] 5–7 типовых запросов с готовым SQL: показания канала за период, все тревоги по объекту за сутки, последнее состояние всех каналов объекта, события в окне вокруг прогноза, срез для витрины.
- [ ] Доступ: какие роли есть, у кого право только на чтение, через какого пользователя подключаться. **Паролей в документе нет** — только имя переменной окружения.
- [ ] Ограничения: что в данных недостоверно и за какой период (итог [TF-1, шаг 3](TF-1.md)).

**1.2. Для того, кто встраивает нас или встраивается к нам**

- [ ] Таблица точек интеграции:

| Направление | Источник / приёмник | Способ | Формат | Режим |
|---|---|---|---|---|
| входящее | СМВУ — потоковые данные | API / очередь сообщений | JSON | только чтение, near real-time |
| входящее | Журналы ОДС | API | JSON / XML | только чтение |
| входящее | Реестр оборудования | API или файл | CSV / XLSX | синхронизация по расписанию |
| входящее | Метеослужба (отложено) | открытый API | JSON | только чтение |
| исходящее | Внешняя система-потребитель | наш REST API | JSON | чтение прогнозов и событий |
| исходящее | Выгрузка для аналитика | файл | CSV / XLSX | по запросу |
| геоданные | карта объектов | наш REST API | GeoJSON / WKT | чтение |

- [ ] Для каждого входящего источника: что делаем, если он недоступен — работаем на последних данных, пишем в журнал, показываем возраст данных в интерфейсе.
- [ ] Правила совместимости: версия в адресе (`/api/v1`), новые поля добавляем — старые не удаляем и не переименовываем, неизвестное поле потребитель игнорирует.
- [ ] Ошибки: единый формат тела ответа при ошибке, коды и что по каждому делать интегратору.
- [ ] **Обезличивание — на стороне источника** ([ТЗ, раздел 2.4](../docs/ТЗ.md)). Записать явно: персональных данных мы не принимаем и не храним; если в потоке они появятся — это дефект источника, фиксируем и сообщаем.
- [ ] Перечень использованных библиотек и компонентов начать здесь же — по ТЗ он обязателен при сдаче ([ТЗ, раздел 2.10](../docs/ТЗ.md)).

### 2. Датчики и журнал технических работ

В выгрузке журнала техработ нет. Значит, работаем с двух сторон: восстанавливаем признаки работ по данным и описываем формат журнала, который попросим у Заказчика.

- [ ] **Признаки техработ в данных.** Довести кандидат Н8 из [анализа](../docs/dataset/анализ.md) до правила: пачка событий по соседним каналам одного объекта, рабочее время, снятие с охраны, открытые двери, УИР-Р. Указать порог: сколько событий за какое окно считаем работой бригады. Оценить масштаб — сколько тревог за 2019–2026 попадает под правило.
- [ ] **Формат журнала работ**, который нужен от Заказчика: начало, конец, объект, участок или список каналов, вид работ, исполнитель, плановая или аварийная. Отдельно отметить минимальный набор полей — чего достаточно, чтобы включить маскирование.
- [ ] **Таблица решений по типам датчиков.** Для каждого из 19 типов из [справочника](../docs/dataset/описание.md) — строка:

| Тип датчика | В режиме работ | Почему | Что видит диспетчер |
|---|---|---|---|
| Газовый датчик | активен | при людях внизу — первый по опасности | тревога как обычно |
| Датчик дыма | активен | пожар работами не отменяется | тревога как обычно |
| Тепловой датчик | активен | | |
| Датчик затопления | активен | | |
| Состояние фазы | активен | | |
| Ручной извещатель | активен | нажимает человек — это всегда сигнал | тревога как обычно |
| КД Дверь, КД Люк | фоново | бригада открывает двери по работе | свёрнуто в «идут работы» |
| Датчик движения | фоново | | |
| Состояние охраны | фоново | | |
| … остальные типы | | | |

- [ ] Правило заполнения: **если сомневаешься — оставляй активным.** Пропущенный пожар дороже лишней карточки у диспетчера.
- [ ] **Что значит «заглушить фоново»** — расписать явно: событие **пишется в БД без изменений**, получает метку `maintenance_window` и не поднимает карточку у диспетчера; свёрнутая строка «идут работы, N событий» разворачивается в полный список. Ничего не удаляем и не правим ([ТЗ, раздел 2.9](../docs/ТЗ.md)).
- [ ] Что происходит с такими событиями при обучении: исключаем из положительных примеров, но оставляем отдельным классом — Захару в [TF-3](TF-3.md) это нужно как метка, а не как удаление.
- [ ] Отдельный пункт: **аварийная работа**. Бригада приехала по инциденту — маскировать нельзя, это как раз «след выезда бригады», по которому мы подтверждаем реальные события. Как отличить от плановой: была ли тревога **до** прибытия.

### 3. Разбиение потока на каналы при выдаче через API

Диспетчеру, аналитику и внешней системе нужен разный срез одного потока. Описать, по каким осям он режется.

- [ ] Оси разбиения и что даёт каждая: тип инженерной системы (6 значений), объект и участок, тип датчика (19), критичность события, признак «маскировано работами».
- [ ] Для `GET /api/v1/events` и `GET /api/v1/readings` — таблица параметров:

| Параметр | Тип | Обязателен | Смысл | По умолчанию |
|---|---|---|---|---|
| `from`, `to` | время ISO 8601 | да | окно времени | — |
| `channel_id` | список | нет | конкретные каналы | все |
| `object_id` | список | нет | объект и всё под ним | все |
| `system_type` | список | нет | инженерная система | все |
| `alarm_only` | булево | нет | только тревожные | `false` |
| `include_maintenance` | булево | нет | показывать маскированные работами | `false` |
| `cursor` | строка | нет | продолжение выдачи | — |
| `limit` | целое | нет | размер страницы | 1000 |

- [ ] **Постраничность через курсор, а не через смещение**: поток дописывается во время чтения, смещение начнёт терять и дублировать записи. Описать, из чего собирается курсор и почему он устойчив.
- [ ] Сортировка по умолчанию и гарантия порядка: годовые журналы **не отсортированы по времени** ([описание](../docs/dataset/описание.md)) — сказать, сортируем ли на выдаче и по какому полю.
- [ ] Ограничение размера ответа: максимум записей за раз и что отвечаем на слишком широкий запрос вместо выгрузки миллиона строк.
- [ ] Подписка на живой поток: темы вида «объект → тип системы», что приходит в сообщении, что делать при разрыве связи — дочитать пропуск обычным `GET` по `from`.
- [ ] Имена параметров согласовать с Гришей **до того**, как он зафиксирует их в Swagger.

### 4. Теоретическая записка: как аналитик читает поток

Отдельный короткий документ — ответ на вопрос «что происходит между датчиком и глазами аналитика».

- [ ] Схема пути данных, Mermaid: датчик → СМВУ → наш приёмник → нормализация и разбор значения → БД (оперативный контур) → API → потребитель. На каждой стрелке — формат и задержка; суммарная задержка должна укладываться в **5 минут** ([ТЗ, раздел 2.5](../docs/ТЗ.md)).
- [ ] Где в этой цепочке что закрыто:
  - канал наружу — **TLS 1.2 и выше** ([ТЗ, раздел 2.8](../docs/ТЗ.md)); шифруется транспорт, а не отдельные поля;
  - TLS снимается на nginx, дальше внутри контура — обычный HTTP между своими сервисами;
  - обезличивание — **до нас**, на стороне источника;
  - кто что может читать — решает роль (RBAC), каждое обращение пишется в журнал действий.
- [ ] Из этого следует вывод, который написать прямым текстом: **аналитик ничего не расшифровывает руками** — он приходит с токеном по HTTPS и получает уже разобранные данные.
- [ ] Три способа доступа для аналитика, с указанием, когда какой:

| Способ | Когда | Что получает |
|---|---|---|
| дашборд | посмотреть текущее состояние и риски | готовые срезы и карта |
| `GET` по API с курсором | своя выборка, повторяемый разбор | JSON постранично |
| выгрузка файлом | посчитать в Excel или ноутбуке | CSV / XLSX |

- [ ] Что аналитик видит и чего не видит: сырое значение канала, нормализованное значение, метка шума, метка режима работ, прогноз с вероятностью и горизонтом. Явно — потока «как есть, без обработки» наружу не отдаём.
- [ ] Сквозной пример: одно событие газового датчика — как оно выглядит в исходном виде, что с ним делает нормализация, что вернёт API, что увидит аналитик в таблице.
- [ ] Абзац «чего мы не знаем»: реального потока СМВУ у нас нет, работаем на проигрывателе журнала; какие допущения из этого следуют.
