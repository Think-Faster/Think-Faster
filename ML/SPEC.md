# ML-контур: прогноз инцидентов

Спецификация модели по ТЗ (§4–§6, §9, §11) и задачам Ф3-1…Ф3-3, Ф5-1, Ф5-5 из `tasks/todo.md`.
Код — `ML/pipeline/`, числа и разборы — `ML/results/`.

## 1. Что прогнозируем

| | Решение | Откуда |
|---|---|---|
| Объект прогноза | объект 3-го уровня (78 шт.), коллектор — объект 2-го уровня (16 шт.) | справочники `docs/dataset/` |
| Единица | объект × час | — |
| Момент прогноза | конец часа h; признаки видят только события, известные к этому моменту | Ф3-1 |
| Цель | начнётся ли эпизод типа k в часах h+1 … h+H | ТЗ §6 |
| Горизонт H | 24 ч по умолчанию, настраивается без пересборки витрины (хранится «через сколько часов следующий эпизод», до 30 сут) | ТЗ §6, §9: не менее 24 ч; Ф5-3 |
| Выход | вероятность по каждому типу, горизонт, объект, признаки-основания | ТЗ §5, Ф3-4 |

**Молчание там, где работает бригада.** Алерт не выдаётся на объект, где в этот момент идут работы:
инженер сам вызывает сработки, которые он же и видит. Отметки о работах в данных нет — её надо
заводить в систему из нарядов и заявок на ТО (объект, начало, конец, исполнитель); это не ML-часть,
но ML-контур обязан её учитывать. Пока отметки нет, работы опознаются косвенно: объект снят с охраны
или недавно начался визит. Цена такого правила посчитана в `results/analytics.md`, раздел 8.

**Типы.** Пожар (`fire`), подтопление (`flood`), отказ оборудования (`equipment`), отказ датчика
(`sensor`), проникновение (`intrusion`) — по ТЗ. Сверх ТЗ предлагаем шестой тип — загазованность
(`gas`). Реакция на газ своя (вентиляция, а не пожарный расчёт), а в пожар газ добавил бы 600
эпизодов за 2022–2025 к 2 554 пожарным. Если заказчик против, газ сливается с пожаром на этапе
разметки, витрина при этом не меняется.

**Отдельная модель отказа датчика** (Ф3-3) — канал × сутки: какой из исправных сейчас датчиков
откажет в ближайшие 7 суток, со второй постановкой на 1 сутки. Семь суток — срок, за который
замену успевают включить в план ТО (Ф5-4).

Цель — только одиночные отказы: в эти сутки на объекте отказали меньше 3 каналов (`MASS`). Это
износ самого датчика, и его меняют по плану ТО. Массовый отказ — десятки и сотни каналов объекта
за сутки: шлейф, контроллер или питание. На массовые сутки приходится 85–90% канало-суток
с отказом. Их ловит основная модель (тип `sensor`), здесь они только признак объекта. Для
сравнения обучена и постановка «любой отказ» (`--target fault`).

## 3. Разметка (`labels.py`, Ф3-2)

Подтверждений инцидентов в данных нет (ответ 12), поэтому разметка косвенная.

1. **Триггер** — строка журнала, которая по смыслу относится к типу: «Обнаружен дым», «Затоплен»,
   «Неисправен» у насоса и т. д. Полный список — `TRIGGERS` в `labels.py`.
2. **Эпизод** — триггеры одного типа на одном объекте с паузой не больше 1 ч. Начало эпизода — момент инцидента.
3. **Шум размечается, но в цель не входит.** Н8 — массовый дым: 10 и больше извещателей объекта
   за ±10 мин. Н7 — «Затоплен» в пределах 60 с после события питания в коллекторе. В 94–100%
   случаев это та же секунда.
4. **Проникновение** — дверь или люк открылись под охраной, за ними сработало движение, а охрану
   в течение 15 мин не сняли. Если сняли, это персонал: в разные годы таких от 4% до 69%
   срабатываний под охраной. Постановка и снятие охраны в одну секунду (28 раз за все годы) —
   мигание, состояние после него то же, что до. Такие пары выкидываются, иначе разметка зависит
   от порядка строк и не воспроизводится.
5. **След выезда** — в том же коллекторе «охрана снята → дверь → движение» с шагом не больше 30 мин.
   Эпизод подтверждён, если выезд начался в пределах **2 ч**. Окно выбрано по приросту доли
   выездов над фоном — фоном служит тот же момент неделей раньше и неделей позже (`results/labels.md`).
6. **Цели модели:**
   - все эпизоды без шума — основная цель;
   - первичные (`_prim`) — такого же типа на объекте не было 7 суток;
   - подтверждённые выездом (`_conf`).

## 4. Признаки (`features.py`, Ф3-1)

- Счётчики состояний в окнах 1 ч / 6 ч / 24 ч / 7 сут: дым, газ, температура, двери, движение,
  питание, насосы, «Неисправен», «Неопределен» и т. д. Дребезг — смены состояния в окне.
- Газ и температура: максимум, среднее, тренд; сколько часов нет показаний.
- Эпизоды и триггеры по типам и шум Н7/Н8 — по объекту и по всему коллектору. Часы с последнего эпизода каждого типа.
- Выезды бригады в коллекторе, вход персонала под охраной, режим охраны и время с его смены.
- Календарь: час, день недели, сезон, праздники и длинные каникулы, 9 мая (ответ 23), дни до праздника.
- Состав объекта: число каналов по типам датчиков.

**Без заглядывания в будущее.** Часть разметки смотрит немного вперёд: Н8 — на 10 мин, персонал
при проникновении — на 15 мин, след выезда — на 30 мин. Такое событие попадает в признаки в тот
момент, когда о нём можно знать (`KNOWN`), а не в момент начала. Проверка — `check.py`: признаки
и цели случайных объекто-часов пересчитываются прямыми запросами к журналу и сверяются с витриной
(`results/check.md`).

Витрина: 3,36 млн строк. В неё входят часы, в которые у объекта были события за прошедшие 7 суток.
Первая неделя данных и первая неделя после каждой дыры отбрасываются, пока окна не заполнились.

## 5. Валидация (Ф3-3)

| Выборка | Годы | Для чего |
|---|---|---|
| обучение | 2022–2024 (ветка `long` добавляет 2019–2020) | обучение |
| проверка | 2025 | ранняя остановка, подбор гиперпараметров, порог, калибровка |
| тест | 2026, январь–июнь | один прогон, ничего по нему не подбирается |

- **Порог тревоги** — лучший F1 на проверке. На тест он переносится без изменений.
- **Обучение** — каждый третий час: соседние часы почти одинаковы. Проверка и тест — все часы.

## 6. Метрики

Инцидентов мало (от 0,1% до 9% объекто-часов в зависимости от типа), поэтому главная метрика —
**PR-AUC**, а не точность и не ROC-AUC. Метрики считаются в двух разрезах.

- **По объекто-часам:**
  - Precision — доля тревожных часов, за которыми в пределах H начался эпизод;
  - Recall — доля часов перед эпизодом, в которые горела тревога.
- **По эпизодам:**
  - Recall — эпизод пойман, если хотя бы в один из H часов перед ним горела тревога;
  - упреждение — сколько часов от первой такой тревоги до начала эпизода (медиана, квартили, доля ≥ 12 ч).
- **Длина непрерывной тревоги к началу эпизода** — до 7 суток. Длинная серия значит, что объект
  давно в зоне риска, а не что модель заметила что-то новое. Без этой метрики упреждение почти
  всегда равно H и ничего не говорит.
- **Калибровка** — ECE после изотонической калибровки на проверке.
- **Бюджет проверок (модель отказа датчика).** Бригада не может каждый день проверять все датчики,
  поэтому считаем, что каждые сутки она проверяет 0,5% или 2% исправных датчиков с наибольшим
  риском. Нагрузка у всех моделей одинаковая, равные оценки базовых уровней разводятся случайно.
  Отказ пойман, если датчик был в списке на проверку хотя бы в одни из H суток перед отказом.

- **Уверенность прогноза** — что показываем диспетчеру рядом с тревогой: калиброванная вероятность
  (изотоническая регрессия на проверке), согласие XGBoost и CatBoost, длительность тревоги, число
  сработавших каналов рядом. Каждый признак проверен на тесте по доле подтвердившихся сигналов,
  разбор — `results/analytics.md`, раздел 6.

Целевые Precision и Recall ТЗ оставляет на этап проектирования (§9). Мы фиксируем их по результатам
теста: для каждого типа в `results/models.md` указан порог и то, что он дал на 2026 году.

**Рабочая точка, которую ставим.** Она выбрана не по метрике, а по цене ошибки у диспетчера, и
разобрана в `results/analytics.md`, раздел 16. Коротко: пожар и подтопление — рабочий порог без
фильтров, отказ оборудования — вторая ступень «сохранить 0,70», отказ датчика и загазованность —
порог q90, проникновение прогнозом не покрывается и идёт только каналом «по факту». На полугодии
теста это 838 сигналов прогноза, из них 304 ложных (1,68 в сутки на 78 объектов), ноль потерянных
происшествий и 60,0% из них — с суточной форой. Прогноз при этом настроен не на максимум полноты:
полноту закрывает второй канал, а прогноз отвечает за фору.

## 7. Модели

| Модель | Где | Зачем |
|---|---|---|
| `freq` | — | частота инцидентов объекта на обучении: сколько даёт знание «где обычно ломается» |
| `rules` | — | правило диспетчера: были ли триггеры этого типа за последние 24 ч |
| `recency` | — | часы с прошлого эпизода этого типа |
| XGBoost | GPU | основная модель. Гиперпараметры подбираются Optuna по PR-AUC проверки (`tune.py`) |
| CatBoost | GPU | сравнение |
| LightGBM | CPU | по плану Ф3-3. В pip-сборке нет CUDA, поэтому идёт на CPU отдельным процессом |
| TCN | GPU | причинные свёртки по часовым рядам объекта за 7 суток, одна сеть на все типы (`seqmodel.py`) |
| отказ датчика | GPU | XGBoost по каналу × суткам (`sensor.py`) |

**Правило выбора.** Для каждого типа в демо идёт модель, лучшая по PR-AUC на проверке — на тесте
ничего не выбирается. Её числа на тесте приводятся как есть. Если на тесте она не обгоняет правила,
в демо идут правила, и это записано в `results/models.md`.

## 8. Обучение на видеокарте

Правила — как в btc-prediction: всё, что умеет GPU, считается на GPU.

- XGBoost — `device=cuda`, `QuantileDMatrix`. Матрица квантуется один раз, между типами меняется только метка.
- CatBoost — `task_type=GPU`.
- TCN:
  - смешанная точность bf16;
  - `pos_weight = √(neg/pos)`, ограничен сверху 10;
  - лучшее состояние сохраняется по PR-AUC проверки.
- Каждый фоновый прогон — под наблюдением. Лог фильтруется на прогресс и `Traceback | Error | OOM |
  out of memory | Killed`, загрузка карты проверяется через `nvidia-smi`.

Отклонения от правил btc-prediction:

- **LightGBM на CPU** — причина в разделе 7.
- **У TCN нет DataLoader и процессов-загрузчиков.** Ряды всех объектов целиком лежат в памяти
  видеокарты: около 0,7 ГБ в fp16. Окна режутся индексами прямо на GPU. В btc загрузчики
  разгружали подготовку батчей на CPU, здесь её нет.

Железо, на котором получены числа: RTX 3050 Laptop 4 ГБ.

## 9. Ретропрогон и погода (Ф5-1, Ф5-5)

- **Ретропрогон 2026 года** (`retro.py`). Каждые сутки 2026 года в 07:00, к началу смены,
  журнал обрезается по этот момент. Берётся 100 суток журнала и вся история режима охраны. По
  обрезанному журналу заново строятся разметка и часовые ряды, модели дают прогноз на 24 ч.
  - Проверка на заглядывание в будущее: вектор признаков из обрезанного журнала сравнивается со
    строкой витрины за тот же час. Любое расхождение означает, что признак видел больше, чем
    знала система в момент прогноза.
  - Для каждых суток сохраняются прогноз и факт. Считаются тревоги в сутки, Precision, Recall по
    объекто-суткам и медианное упреждение, отдельно для моделей и для правил.
  - Ручную проверку «нет признаков из будущего» делает второй человек.
- **Погода Open-Meteo** (температура, осадки, давление по Москве) — только после ретропрогона.
  Прирост считается отдельно по подтоплениям и по пожарной подсистеме. Если прироста нет, так и
  пишем, признаки не тащим.
  - **Сделано, прироста нет.** Подтопление: 0,674 против 0,674 на проверке. Пожарная подсистема:
    хуже во всех четырёх парах. Признаки погоды в модель не взяты, `weather.py` оставлен, чтобы
    проверку можно было повторить. Числа и причина — `results/analytics.md`.
  - Там же — остальные заходы сверх ТЗ: качество воздуха, расширенный набор погоды, обучение на
    семи годах, связки датчиков одного объекта.

## 10. Как воспроизвести

```bash
export TF_JOURNAL=<папка с ext-journal-*.csv>   # журналы в git не лежат
export TF_WORK=<рабочая папка>                  # по умолчанию ML/work, git её не видит
cd ML/pipeline
python events.py          # 1. журнал → ev
python labels.py          # 2. триггеры, эпизоды, шум, выезды
python features.py        # 3. витрина и ряды для нейросети
python check.py 10        #    сверка витрины с журналом
python label_stats.py     #    числа для обоснования разметки
python tune.py --model xgb --trials 40 --rounds 100 --early 20   # 5. подбор гиперпараметров
python tune.py --model cat --trials 30 --rounds 100 --early 20
python train.py --models xgb,cat --params tuned --rounds 100 --early 20   # 4. бустинг
python train.py --models lgbm                      #    LightGBM на CPU
python seqmodel.py --epochs 12                     # 6. нейросеть
python sensor.py build                             # 7. отказ датчика: канал × сутки
python sensor.py train --horizon 7                 #    одиночные отказы на 7 суток
python sensor.py train --horizon 1                 #    …и на 1 сутки
python sensor.py train --horizon 7 --target fault  #    любые отказы, для сравнения
python retro.py --run main_h24_tuned_r100e20 > ../work/retro.md   # 8. ретропрогон 2026 года
```

аналитики показал, что на полном бюджете модель переучивается и даёт у пожара втрое больше ложных
сигналов при той же полноте. Итоговая конфигурация (раздел 16) снята с прогона
`main_h24_tuned_r100e20`; умолчание в коде оставлено прежним, чтобы старые прогоны
воспроизводились по своим тегам.
